## Project Commands

**WorkHub** — a Vietnamese-language internal process/task tracker. Plain Node.js server + vanilla-JS SPA. No build step, no bundler, no `package.json`, no npm dependencies.

```bash
node server.js                              # run: http://localhost:8080
PORT=3000 node server.js                    # custom port (bash)
WORKHUB_DATA=/path/to/data node server.js   # custom data dir (bash)
```

```powershell
$env:PORT = "3000"; node server.js          # custom port (PowerShell)
$env:WORKHUB_DATA = "D:\data\workhub"; node server.js
```

- Requires Node ≥ 18 (uses `for await...of`, `fsp.rm`, `fs.promises`).
- Opening `index.html` directly via `file://` breaks the Processes view — `fetch()` of `processes/*.json` is blocked by CORS. Always serve through `node server.js`.
- No test suite, linter, or build/watch tooling exists in this repo.

## Architecture

**Two runtime halves, both required together:**

1. **`server.js`** — a dependency-free Node HTTP server with two jobs:
   - Serves static files (`index.html`, `assets/`, `processes/*.json`) from the repo root.
   - Serves a small REST API (`/api/info`, `/api/tasks`, `/api/tasks/:id`, `/api/tasks/:id/files...`) that persists task data as JSON files under `./tasks/<task-id>/task.json`, with attachments in `./tasks/<task-id>/files/`. `WORKHUB_DATA` env var overrides the data root. `safeSeg()` guards every path segment against traversal (`..`, slashes).
   - There is no database — the task list on disk *is* the data model; `loadAll()` just globs every subdirectory of the data dir for a `task.json`.

2. **Front end** (`index.html` + `assets/js/*.js`) — no framework, no modules/bundler. Each `assets/js/*.js` file is an IIFE that attaches one global (`window.Store`, `window.UI`, `window.ApiStore`, `window.Processes`, `window.Pipeline`, `window.Tasks`, `window.DeskSvg`, `window.DeskCity`, `window.DeskRoom`, `window.DeskScene`, `window.Desk`, `window.Avatar`), loaded via plain `<script>` tags in this order (dependency order matters — later files call into earlier globals):
   - `storage.js` → `Store`/`UI`: localStorage prefs/theme, export/import, and shared DOM helpers (`UI.el` for building elements, `UI.esc`/`escWithLinks` for escaping — **all dynamic content must go through these**, there's no framework auto-escaping).
   - `rte.js` → `Rte`: Word-like rich-text editor (`contenteditable` + `document.execCommand` toolbar) used for every free-text field: task AC (`t.ac`), notes, changes, golive, mail bodies, todos, documents (`desc`), BRS/DD doc `note` and version `changeSummary`, integration notes and handover `note`. Convention: `fmt: "html"` on an object means **its single free-text field** is HTML; objects without that flag are legacy plain text and still render via `escWithLinks` — no migration. **All stored HTML goes through `Rte.sanitize()` (tag whitelist, no attributes except http(s) `href`) both on save and on render** — never assign an entry's HTML to `innerHTML` any other way. Edit-in-place goes through `tasks.js` helpers `inlineEditBtn`/`inlineEditBlock`/`isEditingEntry` (exposed to `brs.js` as `ctx.editBtn`/`ctx.editBlock`/`ctx.isEditing`); `entryCard` uses them for collections in `RTE_FIELD`, and documents use a multi-field `docEditForm` (`CUSTOM_EDIT`). The in-progress edit id `editingEntryId` is shared render-only state, never persisted.
   - `apistore.js` → `ApiStore`: thin `fetch()` wrapper around the server's task API.
   - `processes.js` → `Processes`: fetches `processes/index.json` (manifest — browsers can't list a directory, so new process files must be registered there) then each listed process JSON, and **generically renders arbitrary JSON** into the Quy trình (Processes) detail view — object keys become sections via `renderValue`/`renderObjectCard`, with Vietnamese labels from a `LABELS` map. Adding a new field to a process JSON schema needs no JS change; it just renders generically (add a `LABELS` entry for a nicer title).
   - `pipeline.js` → `Pipeline`: renders a task's progress across a fixed, hardcoded stage list (`CORE_STAGE_IDS`). Ids are looked up in the loaded processes only for a display name — several (`analysis`, `code-review`, `testing`, `golive`) have no process file and just show the raw id. A task stores its progress as `task.stage`, a **numeric index** into this array, so reordering or inserting stages silently shifts every existing task's position.
   - `brs.js` → `Brs`: BRS/DD documents with version history plus out-of-document changes. One collection `t.brs[]` holds both kinds, discriminated by `kind`: **DD** (from the Lead — few versions, rarely changes) and **BRS** (from the BA — many versions, changes often). `versions[0]` is the baseline and the **last version is the one to implement** ("Đang áp dụng"); every version is kept, never overwritten. `t.changes[]` holds changes not yet in a document, each carrying an `authority`: `"Quyết định Lead"` (a valid exception, may be built immediately) or `"Chờ BA cập nhật BRS"` (not yet legitimate — surfaces as a red warning badge). Document precedence, encoded throughout: **Lead decision > DD > BRS > older versions**. The "Thay đổi" timeline **merges both sources at render time** — never store a change twice. Panels receive a `ctx` object from `tasks.js` (`refresh`, `entryCard`, `fileRow`, `fileOpenBtn`, `select`) instead of importing its private helpers.
   - `sheet.js` → `Sheet`: the sub-tasks of a workboard sheet (`t.sheetTasks[]` — each with start/end dates, status, note). Every number shown (duration, days left/overdue, the `x/n xong · TB y%` roll-up) is **computed at render time**, never stored. Inline edits go through `refreshAfterMutation()` → `rerenderDetail()`, which restores the scroll position of both columns so editing a field never jumps the page back to the top (plain `renderDetail()` resets scroll, which is what you want when switching task or tab). The section has two modes: **read** (default — one compact line per sub-task, no inputs at all) and **edit** (one `✎ Sửa` button on the section header, never per row) — the mode flag lives in the module keyed by task id and is never persisted, so toggling it calls `ctx.rerender()` (redraw only) rather than `ctx.refresh()` (which would dirty `updatedAt` and write to disk). Like `brs.js` it takes a `ctx` from `tasks.js` — which also carries `today`, `dayDiff` and the shared `STATUSES` pool so date logic is not duplicated.
   - `tasks.js` → `Tasks`: the bulk of the app (~1000 lines) — task CRUD, detail tabs (overview/BRS/changes/todos/documents/integrations/notes/mails/golive), all mutating through `saveTask()` → `ApiStore.saveTask()` (optimistic, fire-and-forget to disk). Includes `migrate()` for lazily upgrading old task JSON shapes (legacy `activities` → `todos`; missing `brs`/`changes` arrays) on load. Task type drives which identity fields apply: **Feature** carries `sheet` + `boardTask` (from the lead's workboard plan), **Bug** carries `parentTaskId` linking to its Feature task.
   - `desk-svg.js` → `DeskSvg`: shared SVG markup helpers (`t`/`g`, gradients), RGB LED builders (`led`, `ledGlow`) + a **seeded RNG**, so the procedural gaming scene is identical on every load. `VIEW` is the camera frame — the `viewBox` of every scene `<svg>` (wider than the 1920×1080 design space = zoomed out); the room shell must cover all of `VIEW`, and `desk.js` derives px-per-unit (`--u`) from it, so zoom by changing `VIEW` only.
   - `desk-city.js` → `DeskCity`: the night city seen *down* from a high-rise through the glass wall (`GLASS`) — high horizon, river + bridge, rows of rooftops (pools, helipads, beacons) stepping toward the viewer. Parallax layers (sky/far/mid/near, each with a `depth`), looping traffic strips on the avenues, rain sheets, plus static droplets/reflections on the glass. Lit windows are merged into a few `<path>`s; glows use stacked translucent strokes, not blur filters.
   - `desk-room.js` → `DeskRoom`: the luxury room in one-point perspective (`VP`) — ceiling downlights + cove LED, side walls, polished marble floor, and the floor-to-ceiling glass wall (slim mullions, smoky tint, balcony glass railing, sheer curtains); arc floor lamp and monstera in the corners. Everything outside the glass is opaque, so the city shows through the glass only.
   - `desk-scene.js` → `DeskScene`: assembles the scene (1920×1080 viewBox): city layers, then one room `<svg>` = room + desk + the 5 `.desk-item[data-action]` objects (each with a `.desk-neon` outline pulsing in turn via `--neon-delay`) + "me": the avatar in a gaming chair, 3/4 back view, coffee in hand. Objects are drawn at design size and positioned with `place: [tx, ty, scale]`; their tags are placed unscaled so they stay readable. Avatar parts use classes `av-shirt`/`av-hair`/`av-skin`/`av-glasses` and `[data-avatar-text]` — never hardcode their colours.
   - `avatar.js` → `Avatar`: customises "me" (shirt text ≤ 16 chars, shirt/hair/skin colours, glasses) via the `NHÂN VẬT` panel in the gaming top bar (shown only on the desk). Stored as pref `avatar`; `sanitize()` validates on load and on every input (hex colours only, boolean glasses, text via `textContent`), so a corrupt pref falls back to defaults. Applied as `--av-*` CSS vars + `.no-glasses` on `#desk-scene` — no scene rebuild.
   - `desk.js` → `Desk`: mounts `DeskScene.build()`; the desk objects are the navigation (monitor → tasks, binders → processes, floppy → export, tray → import, controller → back to normal mode). It owns no logic: `Desk.init(host, handlers)` wires each `data-action` to a callback from `app.js`; `Desk.update(counts)` sets `[data-count]` via `textContent`. `fit()` (ResizeObserver) picks `slice` (cover) at aspect ≥ 1.5 else `meet`, and publishes `--u` (px per scene unit) for CSS loop distances. Parallax: rAF loop with time-based easing (same at 60/144 Hz), only while the pointer moves, off under `prefers-reduced-motion`.
   - **Gaming-scene performance rule** (measured, not guessed): anything that *moves* must be a whole element moved by a CSS transform — parallax `.desk-layer`s and `.desk-anim` loops (traffic, rain) — which the GPU composites without repainting. A transform animated *inside* an `<svg>` (rotating fans, falling drops) re-rasterises the SVG every frame and drops to ~30 fps; inside the room `<svg>` animate **opacity only** (fans are two alternating blade sets, steam fades in stages). Layers with `will-change` are stacking contexts, so `.desk-svg--room` needs `position: relative` or the city paints over it. Stack order (back → front): city `.desk-layer`s → rain → curtains (`DeskRoom.curtains()`: two drapes joined at the top centre, swept to the sides at the floor leaving a triangular opening; whole-`<svg>` **skewX only** pivoting on each drape's outer top corner via `calc(50% ± units × var(--u))`, so the tops stay joined while the hems swing outward) → room `<svg>` (whose smoky glass tint also dims the curtains).
   - `app.js`: bootstrap — wires nav/search/theme/collapse UI, calls `Tasks.init()` + `initFolder()` (checks `/api/info` to confirm the server is reachable, shows a reconnect banner if not) and `Processes.load()` (shows a `file://`/CORS guidance banner if fetch fails). All view switching goes through `showView(name)` (sidebar menu and desk alike). Per-view collapse buttons (list column `[data-list-toggle]`, page header `[data-head-toggle]`) share `wireViewToggle()` and persist as prefs `listCollapsed.<view>` / `headCollapsed.<view>`; a collapsed header still shows the storage bar when it is a warning. **UI mode**: `<html data-mode="normal|gaming">`, persisted as pref `uiMode`. Normal = the sidebar layout; gaming = basement.studio-style dark/orange skin + the desk as landing view (`#view-desk`), sidebar hidden, `← VỀ BÀN` / `Esc` return to the desk. In gaming mode the top bar `.gbar` is an auto-hidden overlay (pure CSS): only its 3px orange edge shows; it slides down on hover, `:focus-within`, or while the avatar panel is open (`:has(.av-panel:not([hidden]))`). Every gaming rule lives in `assets/css/gaming.css` scoped under `:root[data-mode="gaming"]` — it restyles existing views by overriding the CSS tokens, so new components get the skin for free as long as they use `var(--…)` instead of hardcoded colors.

**API surface** (implemented in `server.js`): `GET /api/info`, `GET /api/tasks`, `PUT /api/tasks/:id`, `DELETE /api/tasks/:id`, `POST /api/tasks/:id/files?name=...`, `GET /api/tasks/:id/files/:storedAs`.

**Data model note:** process definitions (`processes/*.json`) are read-only reference content edited by hand (see `processes/readme.md` for the schema and update rules — keep `id`/`order` stable, bump `lastUpdated`/`version` on change, and register new files in `processes/index.json`). Task data (`tasks/`) is runtime-generated and not meant to be hand-edited. Note there is no `.gitignore`, and `tasks/` (including uploaded attachments) is currently tracked in git — don't stage it as part of a code change unless asked.
